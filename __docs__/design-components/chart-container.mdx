# Chart container

A container holds **one chart** with its heading, description, optional controls and data state. Every HSK AI progress, trend or distribution chart uses a clear independent context. Keep the professional separation between a headline number, an explanatory chart and a detailed list. Do not copy Khan Academy's teacher report frame or require a specific web-only chart library in native Android.

## When to use

Use a chart container only when a supported, verified HSK AI measurement genuinely needs a chart: for example, current lesson completion relative to a known goal or activity across multiple recorded dates.

| Use when | HSK AI example |
| --- | --- |
| A pattern is more informative than one number | Verified learning activity across several dates. |
| A measured goal needs its context | Actual completed lessons relative to their known total. |
| A report contains more than one different chart | Give each question its own container with an independent title. |

## When NOT to use

- A single statistic belongs in a <a href="./?path=/docs/design-guidelines-components-data-visualization-summary-cards--docs">summary card</a>.
- An exact list of lessons, attempts or words belongs in a <a href="./?path=/docs/design-guidelines-components-data-visualization-data-tables--docs">table or mobile list</a>.
- A chart with unsupported data, missing coverage or no useful comparison must not be rendered just to decorate the screen.
- Do not combine two unrelated measures in one chart container.

## Sizes

| Size | Context | Rule |
| --- | --- | --- |
| Large | Dedicated progress or reporting view | May include context, an accessible chart, relevant controls and a last-updated label. |
| Small | Profile or learner-home summary | Keep one graphic and a few values; avoid controls and legends that crowd a phone screen. |

On narrow phones, containers follow the available width, approved HSK AI spacing and readable typography. Do not use a two-column desktop layout or force a small chart to remain beside another when the labels do not fit.

## Anatomy

| Part | Required | Purpose |
| --- | --- | --- |
| Section heading | On detailed reports | Names the topic, such as learning activity. |
| Chart title | Yes when chart has data | States a verified insight rather than a generic category. |
| Description | When needed | Defines the learner, date range, units or applicable filter. |
| Data marks/axes | Yes | Display the actual values and a comprehensible scale. |
| Legend | Only when direct labels are insufficient | Explain series without relying on color alone. |
| Controls | Optional | Change a valid time range or a supported view. |
| Footer/last update | When data is time-sensitive or asynchronous | Distinguish current, delayed, processed and incomplete information. |

See <a href="./?path=/docs/design-guidelines-foundations-data-visualization--docs#anatomy">Data visualization anatomy</a>.

### Headings

A heading names the section. A chart title communicates the observed conclusion. Keep both concise and grounded in the actual data.

## Controls

Only show working controls. On mobile, controls may wrap below the title or move to a separate clearly labeled row; the original desktop requirement that all controls remain on the same horizontal line does not apply.

| Control | Use when |
| --- | --- |
| Date filter | The dataset actually supports the requested dates. |
| Chart/table switch | Both representations exist and show precisely the same data scope. |
| Export | Export is implemented and permitted for that learner or administrator. |

Never display a disabled mock control as though the product offers it.

### Chart and table toggle

When implemented, preserve the selected range, filters, totals, inclusion rules and state when switching between chart and table. A chart total must match the corresponding table total. On a phone, an accessible table may be a clearly structured list of the same records.

## States

- **Loading:** show a stable, honest loading state rather than fake data.
- **Empty:** distinguish no activity yet from a zero value, no access and no matching filters.
- **Processing/partial:** identify incomplete or unaudited coverage; never present it as the full population.
- **Error:** display a comprehensible failure and a real retry where possible.
- **Stale:** show the age of the last verified snapshot and avoid implying live data.

See <a href="./?path=/docs/design-guidelines-patterns-data-reports--docs#states">Data reports</a>.

## Accessibility

- Preserve semantic heading order.
- Provide a short textual summary of every chart's main result.
- Label each interactive point or control with its measure, date/range and value.
- Make relevant details available through touch, keyboard and screen readers, not hover alone.
- Show missing data explicitly and retain legibility with enlarged text.

## Implementation boundary

Reuse available HSK AI PWA/Android components and the actual backend records. This specification does not add analytics events, force a charting dependency, or change the current UI without a separate implementation and tests.
