# Data tables

Data tables answer **"Which exact item, what value, and what can I do about it?"** They list individually identifiable records when exact comparison, sorting or action is more useful than an overview chart.

In HSK AI, learner-facing rows may represent actual lessons, vocabulary items, exercise attempts or review records **only where that data is available and authorized**. Administrative tables are a distinct scope and must not expose one learner's data to another. Use existing HSK AI mobile surfaces, typography, spacing and accessible controls; do not copy Khan Academy's school roster layout or Wonder Blocks implementation.

## When to use

| Use when | HSK AI example |
| --- | --- |
| A learner needs an exact record and can act on it | An available lesson history or saved vocabulary list with a review action. |
| Values must be compared item by item | Actual recorded activity dates, correct/incorrect counts or progress status per lesson. |
| An administrator needs to inspect audited records | Authorized analytics entries with clear date, scope, source and state. |

## When NOT to use

| Situation | Recommended alternative | Reason |
| --- | --- | --- |
| The takeaway is one number | A <a href="./?path=/docs/design-guidelines-components-data-visualization-summary-cards--docs#stat-card">summary card</a> | A table hides the headline. |
| The reader needs a time trend | A <a href="./?path=/docs/design-guidelines-components-data-visualization-trend-charts--docs">trend chart</a> | A line better shows change over multiple periods. |
| The reader needs the spread across value ranges | A <a href="./?path=/docs/design-guidelines-components-data-visualization-distribution-charts--docs">distribution chart</a> | A table obscures the shape. |
| A phone screen cannot show useful columns without extreme scrolling | A focused list or details view | Keep the information readable rather than squeezing desktop columns. |

## Variants

### Basic table

Use a short header and ordered rows. Put the field readers scan first: for example **Lesson**, **Word**, or **Date**, depending on the real task.

- Use clear, localized column labels; keep labels concise.
- On iPhone PWA and Android, keep only decision-critical columns visible. Move secondary fields to an accessible row details view where necessary.
- Do not imitate school rosters, teacher names or school-grade tables.
- A row must represent a real underlying item, not a fabricated placeholder displayed as data.

### Table with summary tabs

Add tabs only when distinct, useful groups exist in the actual source. Example: **All / Completed / In progress** for lesson records if those states are implemented and reliably tracked.

| Part | Rule |
| --- | --- |
| Group title | States what the tabs divide, e.g. available lesson records. |
| Counts | Use the same scope, period and underlying source in every tab. |
| All tab | Shows the complete applicable set, with any unclassified or missing records explicitly handled. |
| Group tab | Filters only matching rows and updates the visible result count accurately. |

- Counts must reconcile: do not double-count one item in mutually exclusive groups.
- Do not silently classify missing states as incomplete or failed.
- Announce the active tab and current count to assistive technology.

## Content

### Names and identifiers

Use accurate, understandable learner data: Hanzi plus optional pinyin for a word, or the stored lesson title. Preserve the distinction between an HSK level, a lesson number and a word's mastery state. Do not generate fake people, score categories or records.

For administrative views, identifiers and personal data must be included only when the user is authorized to see them. Do not display unrelated user identities as examples of how the learner screen should look.

### Column alignment

Follow a consistent alignment for the selected language, numeric values and actual table headers. Keep numbers scannable, units explicit and long Chinese text legible. Maintain the original professional requirement that labels and values align predictably; on very narrow screens switch to item cards rather than a confusing compressed grid.

### Missing values

Show **0** only for a confirmed measured zero. Show **—** or a clear localized explanation for unavailable, not recorded, still-processing or unaudited values. Distinguish incomplete data from a completed activity with zero points. Never fabricate Android starts, course completions or unique users to fill a cell. See <a href="./?path=/docs/design-guidelines-foundations-data-visualization--docs#missing-and-zero-values">Missing and zero values</a>.

## In-cell visuals

| Visual | Use for | Rule |
| --- | --- | --- |
| Progress bar | Completion relative to a verified goal or total | Include the actual value and denominator as text. |
| Status badge | A recorded state such as completed or awaiting processing | Text and icon accompany semantic color. |
| Warning flag | A genuine actionable problem, not merely a poor learner score | Explain the issue and next step. |

### Flags

- Place the more severe meaningful status first; no more than two flags per cell.
- Link each flag to a specific field when possible.
- A flag may indicate an actually failed save or unavailable data; **low learning performance is not a system error**.
- Never rely on red/green alone. Use icons and explicit words.

## Interaction

### Sorting

Make a column sortable only when its order is meaningful. Indicate the active sort criterion and direction. Sorting must use stable numeric or date values, not lexical ordering for number strings.

### Row actions

Place applicable actions near the item, or in a clearly labeled overflow menu. Use bulk selection only when supported by a real multi-item action. Touch targets must comply with the approved HSK AI platform standards.

### Long tables

Paginate or incrementally load large datasets; preserve scroll position and selection where appropriate. The original recommendation of displaying **up to 50 rows before pagination** is a sensible upper bound for a data table, not a mandate to render 50 complex rows on a phone at once. Mobile lists should load fewer visible rows when needed for responsiveness.

Never count a repeated fetch or duplicated event as a new unique learning record. The displayed total, filter count and exported total must use the same defined scope.

## States

- **Loading:** distinguish pending data from an empty result.
- **No data yet:** state the actual reason if known; do not claim the learner failed an activity.
- **No matching rows:** keep filters visible and allow clearing them.
- **Partial/processing:** label the available subset and any missing coverage without presenting it as complete.
- **Error:** provide a recoverable action; never silently replace data with zero.
- **No access:** explain the access boundary without leaking another account's records.

See <a href="./?path=/docs/design-guidelines-patterns-data-reports--docs#states">Data reports</a> for consistent states.

## Accessibility

- Expose actual column headers and row relationships to screen readers.
- Make sorting, tabs, menus, filters and pagination keyboard accessible.
- Accessible names for row actions include the related item: **Review lesson 3**, not merely **Review**.
- Do not truncate the only accessible Hanzi, pinyin or amount.
- State warning meaning as text; supply context beyond color or a graphical arrow.
- Prefer a readable card-list representation when the same data cannot fit as a mobile table.

## Implementation boundary

This is design guidance. It does not authorize changes to HSK AI's production analytics, event schema, admin data or lesson history. Validate available data and reporting coverage against the real backend before applying the layout on PWA or Android.
