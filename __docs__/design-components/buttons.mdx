# Buttons

A button clearly signals a specific action and immediately performs that action. The HSK AI button system uses the same purpose-based hierarchy across iPhone PWA and native Android. Keep the original professional rules of one primary action per context, clear affordances, predictable outcomes, accessible interaction, and concise copy. Use **HSK AI's approved brand and product semantics**, not Khan Academy's prebuilt button appearance or learner rewards.

## When to use

Use a button when a learner or administrator performs a command or changes state: start lesson, check answer, continue, save, confirm, retry, or purchase a subscription.

Do not use an action button in place of:
- A text link to another resource or detail page.
- A navigation tab that switches between independent, persistent views.
- A selector or menu whose primary purpose is to show choices rather than carry out an action.

Within a sequential lesson, a **Back**, **Continue**, or **Next** control may be an action button because it changes the current step. Main app navigation remains the navigation component.

## Variants

### Primary button

One primary action per visible screen or interaction context. Its purpose is the most important next action: **Start lesson**, **Check**, **Continue**, **Save**, **Confirm** or **Get Pro** when purchase is the main purpose of that screen. A modal or sheet is a separate interaction context with its own primary button; the screen behind it is inactive.

HSK AI's existing brand-red **Instructive** color family is the primary-button accent in the relevant theme, using production tokens and verified accessible foreground/background pairings. Do not substitute a Khan Academy blue. A brand-red primary button means **continue/act**, **not danger**.

Do not put a primary button on every card when one screen-wide primary action already exists. Do not assign the same prominence to unrelated competing actions.

### Secondary button

Use for a useful alternative to the primary action, such as **Save for later**, **Change option**, or **Continue another way**. Multiple equal-priority alternatives are permissible if the hierarchy remains clear. Use HSK AI's established neutral/secondary styling rather than another strongly colored primary surface.

Do not elevate a trivial navigation link, decorative action, XP display or Pro badge to secondary-button status merely because space is available.

### Tertiary button

Use for low-priority actions within the current flow: **Back**, **Skip** where allowed, **Cancel**, **Close**, **More options**, or an optional configuration action. Distinguish a flow-step action from independent app navigation: destinations use links or navigation controls.

### Neutral icon button

Use for unambiguous compact tools such as **Back**, **Close**, **Search**, **Settings** or **Information**, consistent with the approved HSK AI iconography rule. Keep the hit area large and the icon visually calm. Do not add an unnecessary circular plate, tile, glow or shadow behind an icon when the action is already understandable and usable. Provide an accessible name and state.

### Destructive button

Reserve the distinct **Critical** error/destructive color family for genuinely destructive actions, such as **Delete account** or **Discard unsaved work** after confirmation. This red must remain visually distinguishable from HSK AI's ordinary brand red. Never use the Critical palette for a normal lesson or purchase button.

A failed answer or form error is feedback, not a destructive button. Use error text and a distinct error icon alongside semantic color; retain existing Panda/approved-character correct/incorrect feedback effects.

## HSK AI product contexts

### Lesson and practice

The active task has one obvious next action. Lesson choices, check/continue controls, hints, pronunciation controls and exit actions should follow one hierarchy and not compete visually. **Correct and incorrect answer character reactions, gestures and animations are retained**; a button restyle must not disable or obscure those responses, replace them with a generic icon, or delay progress unnecessarily.

An answer option is a selectable learning control, not automatically a primary action button. Its correct/incorrect/selected state must be distinguishable through content, icon and semantic color. Use the existing lesson components when available.

### Subscription and Pro

A subscription screen can have one purchase/confirm primary action, with visible terms and a clear way to go back. Existing HSK AI Pro, gold, pricing and payment branding remain product-specific; a gold Pro badge or crown is **not** automatically a new generic button class. Do not convert a successful purchase into a destructive-style red action. Honor existing checkout exit, confirmation and resume behavior, including any separately approved offer rules.

### Learning achievements and rewards

XP, streak, HSK-level progress and earned rewards are **information or achievements first**, not copies of Khan Academy's Gems, learner accessory buttons or classroom challenges. Show counts and awards using their approved badge/progress designs. Make a reward clickable only when there is a real action (for example, opening the relevant reward details or claiming an actually supported reward). Do not create an imaginary reward or purchase mechanic to imitate another product.

### Settings, reports and other utility screens

Use the same primary/secondary/tertiary hierarchy in settings, personal profile and progress views. Do not import Khan-specific restrictions that reserve core primary and secondary actions exclusively for classroom learning or forbid their use inside settings and modals.

## Sizing and width

### Minimum touch targets

- **iPhone PWA:** at least **44 × 44 CSS px** clickable area.
- **Native Android:** at least **48 × 48 dp** clickable area.

A small visible icon may sit inside a larger hit area. Visually small utility buttons must still meet the target minimum. The iPhone PWA and Android implementations may use platform-native units but should share the same intended hierarchy.

### Default and compact controls

Use production HSK AI component sizes and spacing tokens. The current shared 4-point spacing scale governs repeatable gaps and padding; do not impose new per-screen measurements without checking component behavior.

Small/compact button **appearance** is suitable for low-emphasis utilities inside a narrow panel, card or list, but compact appearance must never reduce the interactive hit target below the platform minimum.

### Width

Buttons normally fit their short labels. On a single-column mobile lesson, form, purchase or bottom sheet, a **single primary next action may fill the available width**. This is an appropriate, deliberate exception already supported by the original button guidance.

Grouped alternatives should retain clear hierarchy and can sit side by side when labels remain legible; stack them when constrained by screen width, localization or larger text. Avoid arbitrary full-width buttons simply to fill empty space.

## States and feedback

### Rest, focus, press and selected

Make enabled, pressed, focused, selected and unavailable states distinguishable without relying on color alone. Preserve visible focus feedback, safe-area and keyboard behavior. Any press animation should be brief, purposeful and respect reduced motion. Avoid an added decorative elevation or glass backplate without a functional design reason.

### Disabled and unavailable

Disable an action when performing it is impossible or unsafe. If information is missing, tell the learner what is needed instead of presenting a mysterious disabled button with no explanation. Do not use disabled styling to hide valid options.

### Loading and repeated taps

When a button starts an asynchronous operation, display a readable loading/busy state **within that action**. Do not send duplicate requests on repeated taps. Preserve the action's context and announce relevant failures; offer **Retry** when appropriate. Do not replace real content with fake success or a perpetual spinner.

### Success, failure and destructive confirmation

Show an immediate, specific result, using text/icons as well as color. The correct/incorrect Panda/character feedback is retained in lessons. Dangerous irreversible actions require an appropriate confirmation and recovery guidance where possible.

## Iconography

Use the already-approved **Phosphor Icons** family for ordinary new interface icons, while preserving canonical HSK AI-specific approved symbols. Add an icon only if it genuinely clarifies the action; it must not duplicate obvious text or make the button more visually crowded. Place leading icons for the action, trailing icons for status/direction when useful. Icon-only actions require an accessible name and adequate hit area.

Do not copy Khan Academy's Gems, Khanmigo, Khanductor, unlock button artwork or icon combinations into HSK AI.

## Placement and grouping

Place the primary action where the learner expects the next step, taking account of keyboard and mobile safe-area insets. Group related actions by purpose, with a clear visual priority and predictable order. Aim for at most two visible action choices together, occasionally three if genuinely necessary; move lower-priority options into a menu rather than presenting a row of equally loud buttons.

Avoid overlays or decorative elements covering the primary action. Keep approved lesson back/exit behavior and do not silently discard progress or purchases when the learner leaves.

## Copy

- Aim for **1–3 short words** when the user's language permits; clarity is more important than an absolute word limit.
- Prefer a plain, specific action verb. Avoid ambiguous **OK**, long technical descriptions and marketing copy in the button itself.
- Use sentence case in the selected language and omit sentence-ending punctuation.
- Use the same label for the same action across PWA and Android, translated appropriately into HSK AI's supported languages.
- Keep paired actions coherent (for example **Back / Continue**). Do not swap meanings or change the label for the same outcome from screen to screen.

## Implementation and verification

This is a **design-system specification**, not a command to immediately replace production buttons. Check actual PWA and Android components before implementation, document any deviations, and migrate deliberately without breaking navigation, billing, lesson assessment, animation, loading or accessibility. Audit both platforms for minimum hit targets, duplicate requests, consistent labels, focus states, contrast, correct/incorrect feedback, and the distinction between brand-red action and Critical destructive red.

Reuse the existing shared mobile components and brand tokens wherever possible rather than introducing one-off button styles.
