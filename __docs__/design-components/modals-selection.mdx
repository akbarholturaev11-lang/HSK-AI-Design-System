# Modals - selection

<NeutralBadge label="Complex filtering" />

A secondary control center for multiple or less frequently used filters in HSK AI's learner progress, vocabulary, exercise history and, where applicable, administrative reports. The mobile screen stays uncluttered while the learner configures options in a focused sheet. Only show filters for data and features that the actual product supports.

## <Do /> When to use

Use a selection sheet when several dependent or optional criteria would clutter the available mobile controls. Preserve one-step direct controls when filtering is simple; do not add a complex sheet solely to imitate desktop reporting.

| Use when | Example use |
| --- | --- |
| Housing secondary filters used less frequently than primary anchors | Keeping extra HSK-level, exercise-type or progress-history criteria out of the primary controls when they are available. |
| The filtering interaction combines multiple input types that are too complex for the filter bar | Selecting an available exercise type may reveal a related subtype only if the current HSK AI data supports that relationship. |

## <Dont /> When NOT to use

Avoid the selection sheet when the task is simple enough for an on-screen control. A filter already applied by default must be visible and understandable rather than hidden inside the sheet.

| Don’t use when | Recommended alternative | Rationale |
| --- | --- | --- |
| A filter needs to be pre-selected or always visible | Embedded filter dropdown | If a date or HSK level is preselected, the applied value should remain visible in the main view rather than secretly filtering results. |
| Only one additional filter is needed | Standard dropdown | If only one additional option is needed, use a simple directly accessible choice rather than a new sheet. |
| The user needs to search by keyword | Search field | For dictionary or vocabulary search, keep text search discoverable in the main view rather than hiding it in a filter sheet. |

## States

### Default modal

Opening the sheet shows the current applied selection. Group available secondary filters visibly; do not quietly add unsupported HSK levels, exercise types or account categories.


## Placement

### Common placement

Open the sheet from an accessible "More filters" control adjacent to the relevant list or report; on narrow screens, the trigger need not live inside a desktop-style horizontal filter bar.

When active filters are not otherwise visible, the trigger can display the accurate number of active secondary criteria. Do not count a default state as a user-applied filter unless it actually narrows the visible data.



### Internal layout

Group supported criteria using clear labels such as HSK level, exercise type, learning outcome or date range, only where those criteria really exist. This keeps the sheet understandable without importing school and classroom groupings.


### Footer actions

Keep "Apply filters" accessible in the pinned footer, full-width when appropriate on mobile. Provide "Reset filters" as a lower-priority action with a clear distinction from dismissing the sheet. On narrow screens, stack the controls in logical reading order rather than forcing desktop left/right positions. Neither action may fall behind the keyboard, bottom navigation or home indicator.


## Interaction

When designing the content of the modal, refer to the specific documentation for components like <a href="./?path=/docs/design-guidelines-components-inputs-dropdown-select--docs">dropdowns</a>, <a href="./?path=/docs/design-guidelines-components-inputs-radio-button--docs">radio buttons</a>, <a href="./?path=/docs/design-guidelines-components-inputs-checkbox-group--docs">checkboxes</a>, and <a href="./?path=/docs/design-guidelines-components-inputs-toggle--docs">toggles</a> to ensure input consistency. For backdrop behavior, sizing, and animations, refer to the <a href="./?path=/docs/design-guidelines-components-overlays-modals--docs">Modals documentation</a>.

### Applying changes

Changes remain pending until the learner selects "Apply filters". Dropdowns, checkboxes and switches must not silently update the list or report between edits. This allows several HSK AI filters to be selected without unnecessary requests or partial state.

Closing a filter sheet via its supported close/back gesture discards only uncommitted filter changes and leaves the currently displayed results unchanged. This is safe for optional filtering, so a separate confirmation is not required. The sheet must not discard a real lesson answer, account change or payment state.

Reopening the sheet restores the criteria currently applied to the HSK AI view, not draft values that were abandoned.

### Layout — category labels

On phones, put each short category label above or beside its control, whichever remains readable with enlarged text and HSK AI translations. A separate left-hand label column is appropriate only when the available width supports it.


### Layout — exposed options

On narrow phone screens, keep exposed checkboxes and single-choice options in one readable column. Use two columns only when width and labels allow, without reducing touch-target size or causing truncation.

Use one predictable reading and keyboard focus order. If two columns are used on a wider screen, lay options down the first column before the second so visual, spoken and keyboard order agree.

A section never scrolls on its own. The modal body is the only scrolling region, and the footer is pinned — "Apply filters" stays reachable however long the content runs.

### Toggle behavior

Within the sheet, each switch has a full-width readable row with its label and control aligned predictably. Respect the selected language and adequate touch targets.


### Dynamic content — adaptive controls

Filter options must come from the supported HSK AI data and may vary by the user's lessons and level. For short sets (roughly eight or fewer), expose the choices directly if they fit on mobile; use a dropdown or searchable list for larger sets or long translated labels. Follow the <a href="./?path=/docs/design-guidelines-components-inputs-dropdown-select--docs#exposed-or-dropdown">existing choice guidelines</a> where applicable.

The form is decided when the modal opens and holds until it closes. A control never changes shape while the user is in the modal, even if another selection narrows its options — a control that changes form mid-interaction moves a target the user is aiming at and casts doubt on selections already made.



### Dynamic content — parent/child logic

Support real dependent filters only when the data has such a relationship, such as an exercise subtype available for a selected exercise type. Do not invent dependencies for the HSK AI interface.

The child control is not displayed until the parent holds a value. When the parent changes, the child keeps its value if that value is still available under the new parent, and is cleared if it is not. Never carry forward a child selection the user can no longer see — an orphaned value produces a filter state nothing in the interface explains. When the parent is cleared, or the new parent has no children, the child is removed along with any value it held.

The change happens in the modal, visibly, at the moment the parent changes — not silently on Apply.



### Reset filters behavior

Selecting "Reset filters" restores actual default values for controls, not necessarily empty selections. A default-on switch returns to on. Reset must not erase saved account preferences, lesson progress or quiz answers.

The sheet stays open after Reset; the new choices remain pending until the user selects "Apply filters". The learner may adjust them again or close without changing the report.

Reset is not the same as Clear applied filters in the main view. Clear removes optional active criteria; Reset restores configured defaults. Keep this distinction visible in HSK AI and follow the <a href="./?path=/docs/design-guidelines-components-inputs-clear-filter--docs">Clear filter guidance</a>.
