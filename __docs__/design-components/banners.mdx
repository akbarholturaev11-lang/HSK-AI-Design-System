# Banners

A banner is a prominent **non-modal** message about important state, an unresolved issue, or a meaningful completed transaction. Use it when the learner needs continuing awareness while still being able to use the relevant screen. This standard applies to HSK AI's iPhone PWA and Android app. Use HSK AI's existing semantic colors, icons, spacing and content patterns; do not copy another product's alert artwork or classroom messages.

## When to use

Use a banner when an issue or state affects the current screen, session, or account and must remain visible until it is resolved, acknowledged, or no longer relevant.

| Use when | HSK AI example |
| --- | --- |
| An important account state needs the learner's attention | Verified subscription expiry approaching; show the real date and a valid route to manage access. |
| A persistent issue affects an ongoing task | A lesson result could not be saved; show the save state and a real **Retry** action rather than pretending the result was stored. |
| An important transaction is completed | A confirmed payment is reflected in the learner's actual Pro entitlement; show details only after the server confirms the state. |
| The learner needs an essential one-time notice | A substantive lesson or account policy that affects continued use. |

## When NOT to use

| Situation | Better pattern | Reason |
| --- | --- | --- |
| A routine, short confirmation such as copied text or a saved preference | Brief non-blocking feedback | A persistent alert adds unnecessary noise. |
| A field has a specific validation error | Inline field error | Keep the explanation next to the affected field. |
| An irreversible action requires explicit confirmation | Confirmation dialog or a dedicated flow | The learner must understand the choice before acting. |
| An account problem blocks the whole screen or requires authentication | Relevant account state, full-screen error, or focused dialog | A banner does not safely enforce a blocked task. |
| A new feature or an optional Pro promotion needs an introduction | The approved, contextual HSK AI feature announcement or relevant product surface | Promotional interruptions must not masquerade as urgent warnings. |
| A correct or incorrect answer needs immediate lesson feedback | Existing lesson answer feedback and approved Panda/character reactions | A banner would compete with the active question and must not replace character expressions or animations. |

## Variants

### Critical error / blocker

Use for a serious unresolved failure with a clear consequence, such as an unsaved lesson result after a failed write, a failed account operation, or a service outage affecting the active task. State **what happened**, **what remains unsaved or unavailable**, and **what the learner can do next**. Never claim a payment, answer or progress update succeeded without the authoritative result.

If continued interaction is unsafe, use a properly blocked state or confirmation instead of relying on a banner alone.

### Warning / action required

Use for a credible future risk, such as a server-confirmed expiry or an action that must be completed to retain access. Prefer specific verified dates or account states. An expired subscription and a pending payment are different states; do not mislabel one as the other or assume payment capture from bank authorization alone.

### Success confirmation

Use when an important multi-step operation **really succeeded**, for example a server-confirmed Pro activation or a restored saved lesson result. The text should reflect the resulting real state. Ordinary small successes do not require a persistent banner. A success banner can be dismissed without undoing the success.

### Informational / feature

Use for essential, temporary non-critical information connected to the current context. Optional feature introductions use the separately approved HSK AI feature-announcement flow, including platform-specific eligibility and dismissal behavior; they are not critical or warning banners. Do not repeatedly show an announcement after the learner has already acknowledged the relevant instance.

## States and dismissal

### Dismissal for informational and success banners

Provide a visible close action for completed success and non-critical information. Dismissing the banner changes **only its presentation**, not the account status, payment, entitlement or underlying result. Remember acknowledgment at the appropriate scope when the product already supports it.

### Unresolved critical and warning states

A banner reporting an ongoing problem must not disappear silently while the problem remains active. If hiding it would conceal unsaved work, loss of access, or a safety-relevant failure, keep the status visible until resolution or until the screen enters a truthful alternate error state.

Do not mechanically make every non-critical subscription reminder permanent: distinguish a genuine blocking state from a future reminder the learner can acknowledge. Let the actual verified status determine the urgency.

### Loading and stale data

The state must be derived from the current account/task authority. Use loading or unavailable copy while verification is in progress; never show stale payment status, entitlement, receipt, or learner-specific notices from a different account as confirmed. On account change, stale notices must be cleared. Provide a recoverable error and retry when status cannot be verified.

## Iconography

Each banner uses the standard semantic status icon as well as text and its approved color pairing: **Critical**, **Warning**, **Success**, or **Information**. Preserve the existing separation between HSK AI brand red and the visually distinct destructive/error red. Meaning must not depend on color alone.

Use the approved HSK AI UI iconography and reuse canonical product assets only for their real product role; do not import Khan Academy's mascot or classroom icons into alert states.

## Actions

### One primary action

Offer a single obvious next step: **Retry**, **Review payment**, **Manage subscription**, or **View details**, only if that action is available in the current platform and account state. Use an action button for retrying or completing a task; use a navigation link when it opens another location.

Never show a purchase button on a platform where that purchase method is unavailable. Keep the existing approved HSK AI purchase and platform routing flows; do not invent a new payment path or fee.

### Guide to resolution

A non-dismissible failure needs a relevant, working recovery path where one exists. If the learner cannot resolve the issue immediately, explain the status without implying a nonexistent action; support or later retry can be offered when applicable. Avoid meaningless **OK** buttons and repeated alerts for the same unresolved failure.

## Placement

### Top of affected content

Place the banner at the top of the affected content area, below the relevant header when appropriate. A global account alert may appear near the beginning of the relevant account view. Avoid covering Hanzi, pinyin, answer choices, character feedback, the AI Voice Orb, primary lesson actions, navigation or the keyboard.

Respect iPhone safe areas and Android window insets. The banner should remain legible on narrow screens and with enlarged text; its body may wrap instead of truncating essential information.

### Maximum two visible banners

Prefer one banner. Show no more than two at once in a single view, with **Critical** first and **Warning** next, followed by Success and Information. On a third event, remove or defer an older non-critical notice where safe; **never automatically remove an unresolved critical status** to make room.

If several problems need simultaneous action, organize them in the relevant notification/account screen rather than building an unlimited stack of banners.

## Accessibility

### Contrast and color independence

Meet at least WCAG AA contrast for meaningful text (normally 4.5:1) and non-text status icons/meaningful boundaries (3:1), subject to the relevant content exceptions. The icon, copy and available action must communicate urgency independently of color. Provide accessible labels for close/action controls and readable focus states.

### Announcements and focus

Announce important new states accessibly without repeatedly interrupting reading. A non-modal banner must not trap focus or unexpectedly change the learner's position in an ongoing lesson. Reserve forced focus changes for a genuinely blocking dialog. Do not make character motion or flashing the sole communication of an alert.

## Copy

### State the status directly

Prefer one concise statement of the actual status and one sentence describing recovery when necessary. Use the selected HSK AI language, with the established meaning consistent between PWA and Android. Avoid technical error codes, excessive politeness, exaggerated urgency and invented facts.

Examples of intent, **not hard-coded production strings**:

| Situation | Concise meaning to communicate |
| --- | --- |
| Result not saved | The lesson result was not saved; retry is available. |
| Payment under verification | Payment status is still being checked; do not claim Pro is already active. |
| Confirmed Pro activation | Pro is now active; state the verified entitlement or period if the server supplies it. |
| Access expiry approaching | Access ends on the confirmed date; manage subscription if that route is available. |
| Offline or service failure | Explain what is unavailable and whether work is preserved locally. |

### Problem to solution

For Critical and Warning banners, the proposed action must actually address the stated problem. Do not label a disconnected route as the solution. Use specific verified amounts, dates, durations or identifiers **only when safely available**, avoiding unnecessary personal or payment information in notifications.

### Punctuation and consistency

Keep short alert text scannable, use sentence case and appropriate punctuation for the learner's language, and translate the meaning rather than copying another app's school-specific English text.

## Implementation boundary

This file specifies expected HSK AI alert design. Do not automatically modify the production PWA/Android notification code while preparing these design guidelines. During later UI work, compare with the existing account notices, payment events, PWA announcement flow, error states and Android counterparts, and test that alert changes do not break lesson progress, billing, account ownership, dismissal persistence or accessibility.
